# Frappe Studio Security

This document describes the security model of Frappe Studio: where credentials and session
material live, what the network layer may and may not do, how webviews are hardened, and which
operations refuse to run without an explicit confirmation.

Frappe Studio is built on Code-OSS (MIT-licensed, developed by the open source community with
credits owed to its Microsoft contributors) and inherits its security posture; this page
covers what Frappe Studio adds to it.

## Credentials and session material

**Passwords and credentials live only in the operating system secret storage.** Frappe Studio
uses the platform `ISecretStorageService`, which is backed by the OS keychain on
Windows/macOS and equivalent key services (libsecret) on Linux. Secrets are stored under the
service name `frappe-studio`. Nothing secret is ever persisted in application storage,
settings, or files under the user data directory (`dataFolderName` is `.frappe-studio`).

**Session cookies live only in memory.** The `cookieJar.ts` container holds the authenticated
session for connected sites in memory for the lifetime of the process. Cookies are never
written to logs, storage, disk or telemetry. When the workbench closes, session material is
gone.

**CSRF handling.** The CSRF token is fetched from `frappe.auth.get_csrf_token` at connect
time and refreshed on demand (e.g. when a mutating request is rejected with a CSRF error). It
is sent as `X-Frappe-CSRF-Token` on mutating requests. The token is runtime state in the
client, not a stored secret.

**No API keys are ever generated by Frappe Studio.** This is deliberate and worth stating
plainly: Frappe lets users create API keys (API key + API secret pairs) for scripted access.
Frappe Studio does not create, mint, display or store API keys, so there is no path where the
IDE silently becomes a credential factory. Users who want token-based access create keys
themselves inside Frappe, exactly as they always have. The Studio's HTTP client authenticates
with the session cookie only.

**Secrets under a single service name.** All credential records use the secret-service name
`frappe-studio`, and the site list (without secrets) is stored in application storage under
`frappe-studio.connections.v1`. The `trusted` flag — the user's explicit decision to accept a
self-signed certificate for one connection — is part of that site record; see TLS below.

## TLS

Certificate validation is **never silently disabled**. If a site's certificate fails
validation, Frappe Studio shows a clear diagnostic describing the failure (self-signed,
hostname mismatch, expired, unknown authority) — it does not fall back to "just connect".

The only escape hatch is explicit per-connection trust: the connection wizard offers to trust
the offending self-signed certificate for that one connection, with the risk spelled out, and
stores the user's decision as the connection's `trusted` flag. Trusting a certificate is a
user decision, surfaced and reversible, never a default.

An application-level proxy setting exists (upstream Code-OSS proxy config), which applies to
the whole app; Frappe Studio's site requests honor it.

## Webviews

All Frappe Studio webview editors (DocType Studio, Workflow Designer, Print Format Designer,
API Explorer, Report Runner surfaces, Database Explorer panels) plus the connection wizard:
- load no remote resources,
- run only nonce-tagged scripts (strict CSP),
- receive page data through the platform's webview transfer layer — webviews never talk to
  the network themselves; requests go through the authenticated client in the main workbench
  so cookies and CSRF stay out of the webview.

This means a malicious page body from a site cannot exfiltrate the session: the webview has
neither the cookie jar nor the ability to fetch cross-origin.

## Network layer constraint

Network access to sites happens only through `frappeClient.ts`, which targets documented,
whitelisted Frappe endpoints:

- `POST /api/method/login`, `POST /api/method/logout`
- `GET /api/method/frappe.auth.get_logged_user`, `frappe.auth.get_csrf_token`
- `GET /api/method/frappe.get_versions`
- `frappe.client.*` (get, get_list, insert, update, delete)
- `frappe.desk.query_report.run`, `frappe.desk.search.search_link`,
  `frappe.desk.search.search_widget`, desk page (`getdeskpage`)
- REST resource paths `/api/resource/...`, `/api/v2/...`, and the `/printview` route

Frappe Studio **never attempts arbitrary code execution through Frappe endpoints** — no
crafted calls that push script onto the server (no evaluated JS payloads, no `frappe.call`
abuse, no `console` method abuse), regardless of developer mode. Everything it writes is
Frappé document metadata: field definitions, workflow documents, custom fields, property
setters, report bodies, print formats.

## Destructive operations

Every operation that can destroy data goes through an explicit confirmation step:

| Operation | Confirmation |
| --- | --- |
| Delete a Custom Field / Property Setter (customization reset) | explicit confirm, deletes only the customization documents, never the standard DocType |
| Overwrite a DocType with a save that removes fields | validation problems block the save; confirmed diffs are visible in the JSON view |
| Database Explorer destructive SQL | disabled outright, with an explanation (Frappe exposes no raw SQL over HTTP) |
| API Explorer mutating sends (`DELETE`, `PUT`, `POST` that may mutate) | confirmation step before send |
| Bench commands like `migrate`, `drop-site`, `new-site`, backup restore | confirmation in the terminal flow before the command starts |

Running a report is read-only from the Studio's point of view, but a report's implementation
can be anything the site allows; the Studio therefore still confirms destructive intent only
where *it* initiates a write or delete — report execution follows Frappe's own whitelisted
report API with no Studio-side escalation.

## Bench manager

Bench commands run in the integrated terminal in view of the user, with the context's working
directory (via `wsl.exe` for WSL contexts). The Studio does not inject user input into bench
commands unsanitized, does not run hidden commands, and does not modify `common_site_config.json`
directly — enabling developer mode for a local bench runs `bench set-config developer_mode 1`
followed by `bench clear-cache` explicitly in the terminal, with confirmation, and verification
afterwards.

## Reporting a security issue

Please do not open a public GitHub issue for security reports. Open a private security
advisory on the repository (`m7amedenho/frappe-studio`) instead. For issues in Code-OSS
itself, report upstream to `microsoft/vscode`; for issues in Frappe Framework, report
upstream to `frappe/frappe`.
