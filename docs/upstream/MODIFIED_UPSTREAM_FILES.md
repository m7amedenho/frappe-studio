# Modified Upstream Files

This is the **complete and precise** list of files from the upstream Code-OSS checkout that
Frappe Studio modifies. Everything else under `src/`, `build/` and `.github/` is either stock
upstream or an additive file owned by Frappe Studio. Upstream base commit:
`1745a4a6102e93173430b4b2debc1247a91cd036` (Code-OSS 1.146.0 era).

| File | Modification | Reason | Features depending on it | Alternative considered | Merge risk | How to re-apply after upstream update |
| --- | --- | --- | --- | --- | --- | --- |
| `src/vs/workbench/workbench.common.main.ts` | One import line registering `src/vs/workbench/contrib/frappeStudio/frappe.contribution.ts` (same pattern as the git/SCM/debug contributions) | The workbench contribution must be imported for the platform to instantiate it | All Frappe Studio UI: activity-bar container + views, webview editors (DocType Studio, Workflow Designer, API Explorer, Print Format Designer, Report Runner, Database Explorer), commands (`frappeStudio.about` and friends), settings, status-bar connection item, keybindings | An extension (participant in extension host) — rejected: frappeStudio must run natively in the main process for secret storage, providers and terminal integration, and must not depend on extension availability | **High** — an upstream rename or reorganization of `workbench.common.main.ts` silently drops Frappe Studio UI from the workbench (views disappear; the product compiles but no longer integrates); the CI typecheck and test workflows catch the breakage, a human must re-add the line | Re-add the single import line at the end of the file's existing contribution imports, matching the file's import grouping; then run `pnpm run compile` + `pnpm run typecheck-client` + launch and confirm the Frappe Studio activity-bar icon renders |
| `product.json` | Branding identifiers: `nameShort` "Frappe Studio", `nameLong` Frappe Studio, `applicationName` `frappe-studio`, `dataFolderName` `.frappe-studio`, `urlProtocol` `frappe-studio`, plus the `win32*` identifiers (mutex, reg value, app IDs, app-user-model id, dir name, shell name) | Product identity: the fork must not install or configure as Code-OSS, and must be genuinely branded as Frappe Studio (MIT-licensed, based on Code-OSS with acknowledgment of Microsoft contributors — not misleading Microsoft branding) | Every user-visible part: window title, About dialog command surface (`frappeStudio.about`) reads this branding, OS integration (URL protocol handler, Windows registry/mutex names, start-menu/dirs), data-folder isolation so a Code-OSS install and Frappe Studio never share config | An overlay/generator build step that writes branding at package time from a non-upstream file — rejected because `product.json` is read at runtime by the workbench and a divergence between repo and packaged builds invites "works in dev, ships wrong" bugs | **Medium** — upstream does not shuffle these keys often but has historically reorganized them; an upstream product.json change that keeps old keys while adding new ones merges cleanly, a rename/semantic-shift conflicts visibly | Diff a pristine `product.json` from the recorded upstream base against the fork's, re-apply the fork's keys onto the new file (preserving any newly added upstream keys verbatim), then launch and confirm window title, About dialog, and data-folder path (`~/.frappe-studio`) |
| `package.json` | Top-level `name` (`frappe-studio`), `version` (`1.0.0`), and the `frappe-studio:*` npm scripts (the `upstream:*` script family among them, backed by `scripts/upstream/`) | The npm package identity and the product's own tooling entry points | Release workflow (`release.yml` reads name/version), About dialog version display (`frappeStudio.about` reads the product version), all upstream-sync maintenance commands (`npm run upstream:check|fetch|sync|status|report|test`) | Keep `package.json` pristine and put scripts/identity in a separate file — rejected because the build and packaging pipelines read name/version/scripts from the root `package.json` and the repo's Williams-and-similar CI tools key off them | **Medium** — upstream modifies `package.json` frequently (dependency bumps, script additions); the risky spots are the fork's own keys being clobbered (rare) and dependency conflicts (common, resolved per `CONFLICT_POLICY.md`) | After an upstream update, verify the three things upstream edits touch are intact: `name`, `version`, `scripts` — re-apply any missing fork-owned keys, re-run `pnpm install` and `npm run upstream:status` to confirm tooling survives; never delete or relock the fork's `frappe-studio:*` scripts |

## Rules

- This table must be kept exact — it is the checklist for every upstream merge and the health
  reference used by `npm run upstream:status`.
- Anything else under `src/`, `build/`, or `.github/` that seems Frappe Studio-related should
  be either in this table or additive (new files, zero upstream edits). If a *fourth* file ever
  needs editing, that edit goes through review against `docs/upstream/CONFLICT_POLICY.md`
  first, because it expands the merge surface permanently.
- `docs/` and `scripts/upstream/` are entirely additive and not listed above.
